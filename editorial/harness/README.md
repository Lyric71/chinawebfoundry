# Measurement harness

**Blocking for T2 and T4.** Nothing in either tier publishes without an
original measurement from here, carrying a named vantage point and a date.
The full build spec is PLAN.md section 3. This file is the repo-side scaffold
and the operating notes.

## What exists in the repo today (6 September 2026)

| File | What it is |
|---|---|
| `hosts.yml` | The versioned host list, roughly 60 hosts in the categories the published tables use, plus controls. An editorial asset: changes are reviewed, never casual. |
| `probe.mjs` | The tier-one collector. Node 18+, no dependencies. Runs the full host list from wherever it is executed, three attempts per host, 60-second abandon, records TTFB and completion separately, writes one JSON file per run. |
| `runs/` | Raw runs, one file each, named by run_id. Gitignored: they are copied back from the probe machine and archived outside the repo. Keep every raw run indefinitely. |
| `latest.json` | The newest run's rows, committed. The drafts read this. Regenerated by `probe.mjs --latest` from the most recent run file for each vantage point. |

   (阿里云) or Tencent Cloud (腾讯云), mainland region. Not the same cloud as
   anything on the host list that we sell against. Single-digit dollars a
   month. `probe.mjs` runs there on cron, every 6 hours for the curl-style
   pass. The headless Chromium waterfall pass (which is what catches the
   `no_event` case properly) is not written yet; the current probe infers
   `no_event` from a DNS success followed by no connection event inside the
   abandon window.
2. **The tier-two last-mile source.** Tencent Cloud CAT (云拨测) Basic,
   roughly 1,299 yuan a month, 15-day trial, Beijing, Shanghai, Guangzhou and
   Shenzhen last-mile nodes, documented API. Or boce.com (拨测) per check,
   with domain pollution monitoring. A tier-two row is one with
   `vantage.type: "consumer"` and a `carrier`. Until this exists, the
   consumer column in every published table is empty and says so.
3. **The GreatFire cross-check.** Daily scrape, blocked-or-not only, never a
   latency source.
4. **The method page.** Must be published before the first index edition
   (T4-01, week 6).
5. **The build-time consumer.** PLAN.md wants `data/china-hosts-latest.json`

## Running the probe

On the probe machine, from a checkout of this repo:

```
node editorial/harness/probe.mjs --vantage datacenter --provider alibaba-cloud --region cn-zhangjiakou
node editorial/harness/probe.mjs --vantage consumer --provider china-unicom --region beijing --carrier "China Unicom"
node editorial/harness/probe.mjs --latest
```

Options: `--hosts <file>` (default `hosts.yml` next to the script),
`--attempts 3`, `--abandon 60000`, `--only <substring>` to probe a subset,
`--out <dir>` (default `runs/`). Every run writes
`runs/<run_id>-<vantage-type>-<region>.json` with the schema below and prints
a one-line summary per host.

`--latest` rebuilds `latest.json` from the newest run per vantage point.

## Data schema

One row per host, per vantage point, per run. Straight from PLAN.md 3.5.

```json
{
  "run_id": "2026-10-01T02:00:00Z",
  "host": "cdn.mxpnl.com",
  "dependency": "Mixpanel",
  "category": "analytics",
  "vantage": { "type": "datacenter", "provider": "alibaba-cloud", "region": "cn-zhangjiakou", "carrier": null },
  "dns_ms": 34,
  "connect_ms": 128,
  "tls_ms": 210,
  "ttfb_ms": 391,
  "complete_ms": null,
  "outcome": "answered_no_completion",
  "bytes": 0,
  "abandon_after_ms": 60000,
  "http_status": null,
  "resolved_ip": "104.18.x.x",
  "attempts": 3,
  "successes": 0,
  "notes": ""
}
```

`outcome` is a closed enum:

| Value | Meaning |
|---|---|
| `ok` | Completed inside the threshold. |
| `slow` | Completed, but above the category's slow threshold (default 1,000ms TTFB). |
| `answered_no_completion` | First byte received, never finished. The silent killer. |
| `no_response` | Connection attempt, no first byte. |
| `no_event` | The request never produced a connection event at all. |
| `dns_fail` | Resolution failed or returned a poisoned answer. |
| `not_tested` | In the list, not probed this run. Published as such, never omitted. |

## Publication contract

From PLAN.md 3.8. Every published figure carries the number, the vantage
point, the method and the date. TTFB rounded to the nearest 10ms above
100ms. Three runs minimum, successes as a fraction ("0 of 3"), never a
percentage. Never blend vantage points into an average. Never publish a
figure older than 90 days without re-running it.

## Acceptance criteria (PLAN.md 3.10)

- [ ] Tier one instance running in a mainland region, on a different cloud from the primary measurement targets
- [ ] Tier two subscription live, with at least Beijing and Shanghai last-mile nodes
- [ ] `hosts.yml` committed, roughly 60 hosts, grouped and versioned
- [ ] All seven `outcome` values reachable in practice: a known-blocked host returns `no_response` or `no_event`, a known answers-then-hangs host returns `answered_no_completion`
- [ ] The no-event case is detected by diffing expected against observed requests, not by waiting for an error (needs the headless pass)
- [ ] Three attempts per host per run, successes reported as a fraction
- [ ] 60-second abandon threshold enforced and recorded
- [ ] `latest.json` written after every run and committed
- [ ] Monthly snapshot frozen and dated (copy the run files for the month into an archive folder outside the repo, named by edition)
- [ ] The eleven untested dependencies (F42) probed and their rows filled before any T2 page cites them
- [ ] Method page published before the first index edition

## Risks to check before every host list change

Probe co-location (do not measure the cloud the probe runs on). Reading
absence as health (the collector must record what did not arrive). Tier two
lapsing silently (pull the consumer column rather than publish a datacenter
number in its place). CDN edge versus service (`resolved_ip` on every row).
The list becoming the product (sixty hosts measured well beat three hundred
measured once).
